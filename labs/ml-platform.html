Training 1 · One DDP training step: where does the data go, and who calls whom?

4 ranks (one process + one GPU each, torchrun --nproc_per_node=4), a 6-layer model (L1–L6), 3 gradient buckets. The big map is rank 0: CPU (processes + RAM) on top, GPU (memory + 2 streams) below, joined by PCIe. The cards at the bottom are ranks 1–3, doing the same steps at the same time, so you can see what's different (data, gradients) and what's the same (weights). The comm stream is where NCCL, the GPU-to-GPU communication library, runs all-reduce and broadcast. Each press runs one part of the loop: the ● shows data moving, calls shows which functions run, in order, and reads shows which settings they read.


  

  
So what: data is built on the CPU (sampler → workers → pinned RAM), crosses PCIe once per batch at .cuda(), and from then on the tensors stay in GPU memory (the CPU just drives the loop and launches kernels). backward() is run by the autograd engine; DDP joins only through its hooks, and its Reducer hands full buckets to NCCL, which sends them on a separate stream while compute continues. optimizer.step() doesn't involve DDP or any communication.

Training 4 · What does set_epoch change — and why don't ranks overlap?

  
  
10 samples (1–10), 2 ranks. DistributedSampler does 3 things on every rank: ① start from the full list, ② shuffle it with a seed, ③ keep only its own positions (rank 0: 1st, 3rd, 5th… · rank 1: 2nd, 4th, 6th…). The split is by position, not by value.

  

    
    
    
    
  

  

  
  

  
So what: every rank shuffles the whole list by itself — nobody sends it the list. Because they all use the same seed, they all get the same order, and taking different positions of the same order can't overlap. set_epoch(e) changes that shared seed each epoch, so each rank gets different samples every epoch — still disjoint.

Training 8 · Buckets & hooks: when does all-reduce start?

  
  
compute = backward kernels on the GPU (producer). comm = the GPU's comm stream, where NCCL exchanges a full bucket with the other GPUs (consumer). The data travels over NVLink between GPUs in the same machine, or over the network card (InfiniBand / Ethernet) between machines. They run at the same time on separate GPU streams. New to hooks/NCCL? Do Training 1 first.

  
NCCL (NVIDIA Collective Communications Library) is the library that actually moves the data between GPUs. It runs collective operations such as all-reduce and broadcast as GPU kernels and picks the fastest path (NVLink, PCIe or the network). DDP's Reducer only asks for "all-reduce bucket A"; NCCL does it. You select it with init_process_group(backend="nccl").

  
A 6-layer model. backward() runs from the last layer (L6) to the first (L1); each layer's gradient takes 1 time unit. Every all-reduce costs a fixed 1.1 units of overhead + 0.25 per layer it carries. One press = one layer's gradient is ready.

  

    
    
    
  

  

  
  

  

  

    
all-reduce calls0

    
backward + sync time–

  

  

  
So what: a hook is a function autograd calls the moment one parameter's gradient is ready. DDP's hook drops it into its bucket; when a bucket is full, it launches that bucket's all-reduce asynchronously while backward keeps computing earlier layers. Communication overlaps computation. Too few buckets = no overlap; too many = per-call overhead piles up (bucket_cap_mb, default 25 MB, sets the size).

Goal: one weight update from 128 samples per rank. 2 ranks; each backward sends gradients in 2 buckets (buckets: Training 8). Two separate knobs: accumulation (feed 32 at a time, step every 4) cuts memory; no_sync cuts communication.

So what: A is the ideal, but 128 may not fit in GPU memory. B fits (32 at a time) but DDP syncs after every backward → 4× the communication. C keeps B's memory and gets back to A's communication: .grad sums locally because backward adds (+=), so one all-reduce of the sum gives the same average. Keep the last micro-batch outside no_sync, or the ranks never sync.

Linux 1 · What each vmstat number is, in the hardware

  
One machine with 4 CPU cores, RAM and a disk. RAM is managed in pages (4 KB blocks). Pick a column: the map shows what physically happens (tasks on cores, pages moving between RAM and disk), and the vmstat line on top shows which number it makes go up.

  

    
    
    
    
    
  

  
  

  
So what: vmstat counts three kinds of things. Tasks: r = running or waiting for a core, b = stuck waiting for the disk. Time: us / sy / id / wa = how each CPU second was spent. Pages and blocks moving: bi / bo = file data between disk and RAM, si / so = process memory pushed out to swap and pulled back. Read them together, then use Linux 2 to practise.
